# 代码审核方法论（内部）

## 一、分析顺序（按此顺序扫描，不要跳步）

先看**影响面**，再看**理解成本**，再看**重复**，再看**是否过度设计**，
再看**依赖方向**，再看**领域表达是否准确**，最后看**测试**。

顺序的道理：影响面最容易被忽略、代价最大；测试放最后，因为它只是结果，
不是原因。

## 二、六类结构性风险

### 1. 认知负担过重
判断问题：读懂这段代码需要人花多少脑力？
- 函数超过 20 行且混用了多个抽象层次
- 嵌套超过 3 层
- 参数超过 4 个
- 出现魔法数字或未解释的常量
- 变量名要读实现才懂（`d`、`tmp2`、`flag`）
- 布尔表达式并列 3 个以上条件
- 连续链式调用 `a.getB().getC().doD()`
- 代码里的名字和业务方说的不是同一个词
- 布尔参数让一个函数干两件根本不同的事
- 领域概念用裸类型表达（`String email`、`int orderId`、`double money`）
- 模块的接口/文档比它提供的功能还复杂

**不该报**：有清晰命名和卫语句的线性代码；藏在深而简单的模块边界后面的实现细节；
专家确实这么说的领域术语。

### 2. 变更扩散
判断问题：改一处，有多少不相干的东西会跟着坏？
- 改一个功能要动 3 个以上不相干模块的文件
- 一个类为多个不同的业务原因而变化
- 方法用了别的类比自己的类更多的数据
- 两个类直接知道对方的内部状态
- 改一个模块要重测许多不相干模块
- **隐含契约**：被足够多人调用的实现细节（错误文案、调用顺序、未声明的副作用）
  会变成别人依赖的事实契约，尽管从来没承诺过
- **正交性破坏**：加一种支付方式不该顺带改日志、缓存、通知
- **信息泄漏**：同一个设计决策（文件格式、协议细节、数据形状）被编码在多个模块里

**不该报**：组合根里装配具体依赖；有意承诺的稳定公开行为；同一限界上下文内的
协同修改是正常的。

### 3. 知识重复
判断问题：同一个决策是不是被写在了不止一个地方？
- 同样的逻辑被复制到多个文件或函数
- 同一个概念在不同地方有不同名字（`user`/`account`/`member` 指同一个实体）
- 平行的类层次必须同步修改
- 配置值以字面量重复出现在多处
- 两个模块各自独立实现了同一算法

**不该报**：分属不同限界上下文的重复；正在进行的抽取/迁移期间的临时重复；
在明确边界上各自拥有更清晰的共享协议常量。

### 4. 过度设计
判断问题：代码是不是比它要解决的问题更复杂？
- 「为将来预留」但当前没有任何使用方的抽象
- 只包了一层方法调用的类；只做转发的纯中转类
- 第二版系统比第一版复杂得多，为尚不存在的需求增加通用性
- 用 switch 表达本该由多态表达的东西
- 从来没有被改过默认值的配置项
- 框架代码比它承载的业务代码还多
- 长期战术性补丁堆出来的结构：每个临时方案都不大，但加起来每加一个功能都要
  跟既有结构搏斗

**不该报**：对某个外部协议/线格式/封闭枚举做 switch；吸收外部依赖波动、
隐藏不稳定性的薄封装；第二版只有在新增通用性超出当前需要时才算过度设计。

### 5. 依赖失序
判断问题：依赖是不是朝一个方向、可预测地流动？
- 模块/包之间存在循环依赖
- 高层业务逻辑直接 import 低层基础设施（例如领域服务 import 具体数据库驱动）
- 稳定且被广泛使用的组件依赖了不稳定、频繁变化的组件
- 抽象依赖具体
- 违反迪米特法则：`order.getCustomer().getAddress().getCity()`
- 单个模块向外 import 超过 5 个模块
- 实现某个接口却只用其中一部分方法，或被迫为空方法写桩（接口过胖）
- 整个系统「不像一个人设计的」：不同模块用互不兼容的架构风格且没有取舍规则
- 直接锁定传递依赖的版本，升级一个库要协调多个无关方

**不该报**：编排层/组合根的高扇出；显式做跨边界转换的适配器模块；
在依赖策略清晰前提下覆盖多个叶子依赖的稳定外观。

### 6. 领域失真
判断问题：代码有没有忠实表达它要解决的问题？
- 业务逻辑散落在服务层，领域对象只有 getter/setter（贫血模型）
- 代码里的名字和业务方说法不一致
- 一个类只装数据、没有任何行为
- 子类忽略或覆盖掉父类大部分行为（拒绝继承）
- 跨限界上下文却没有做任何转换
- 方法对别的类的数据比对自己的更感兴趣
- 子类用不兼容的行为覆盖父类方法，或在父类承诺成功处抛异常（替换后调用方就坏）
- 把值对象当实体用：本应由属性完全定义的概念（Money、Email、Address）
  被赋予了可变 ID 和生命周期

**不该报**：CRUD 为主的流程用事务脚本；DTO / 持久化记录 / API 载荷模型只装数据；
业务模型本身就简单时，共享的基础设施语言不算领域漂移。

## 三、工程判据（判断「该不该这么写」的尺子）

- **一个决策只存在一处**：同一个决定写在两处，早晚会分叉。
- **边界处校验一次，内部信任**：数据在进入系统的地方检查完，内部不再反复防御。
- **让非法状态无法表达**：用结构（类型、枚举、必填字段）排除掉非法组合，
  而不是靠调用方记得别那么写。
- **操作幂等**：跑两次、或中途崩溃后重跑，最终状态一致。
- **共享可变状态要么各持一份，要么只允许一个写者**，并在结构上强制这一点。
- **修根因**：能复现 → 修掉原因。只把崩溃藏起来的护栏不算修复。
- **测行为不测实现**：测试按使用者调用它的方式调用，检查使用者能看到的结果；
  如果所有函数都返回空测试还能过，这个测试该丢掉。
- **先减后加**：新增之前先拿掉复杂度。

## 四、每条问题必须四段齐全

**现象 → 成因 → 后果 → 修改建议**，缺一段就是噪音：

- **现象**：在代码里**实际看到**了什么（文件、行号、具体写法）。不写推测。
- **成因**：是什么导致它变成这样（结构上的原因，不是「开发不小心」）。
- **后果**：如果不改，会发生什么、谁受影响、为什么值得现在处理。
- **修改建议**：具体到能直接动手的动作。

只列规则违反、不解释为什么值得改的，不算一条问题。

## 五、不要报什么（防误报）

- 没有证据、只是「感觉不好」的不要报。
- 代码已经足够清晰且局部化的，不要为了凑数报。
- 有正当理由的例外（见每类下面「不该报」）不要报。
- 同一根因拆成多条同一问题的，合并成一条。
- 不确定的标「待确认」并写清怎么验证，不要断言。

## 六、报告输出的硬性禁令

报告里**只出现**项目自身的语言。严禁出现：

- 任何方法论、审查框架、检查清单的名称或代号
- 任何书籍、作者、论文、标准、工具、脚本、插件、技能的名称
- 「本报告使用了……方法/流程/框架/工具」这类交代过程的话
- 声称「已修复」「已用工具修复」「已自动改写」代码——审核只给建议，不动代码

需要解释判断依据时，用代码本身的事实说话（「因为 X 处和 Y 处各写了一份同样的
判断，所以改一处会漏另一处」），不要引用外部来源。
